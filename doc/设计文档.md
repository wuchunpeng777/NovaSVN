# NovaSVN 设计文档

## 项目定位

NovaSVN 是一个面向 Subversion 的现代化提交工作台。它不以替代 TortoiseSVN 为目标，也不打算一开始就做成完整的 SVN 客户端。它的核心价值是优化本地改动审查、提交准备、安全检查，以及 SVN 原生体验里比较薄弱的“部分提交”流程。

可选英文标语：

- A focused commit workspace for Subversion.
- A modern Subversion client.
- Subversion workflow, refined.

中文定位：

- 现代化 SVN 工作台
- SVN 提交审查增强工具
- 面向高频提交场景的 Subversion 桌面客户端

## 为什么要做 NovaSVN

TortoiseSVN 已经非常成熟，尤其擅长 Windows Explorer 右键菜单、基础提交、更新、日志、合并等常规操作。NovaSVN 不应该重复造一个完整的 TortoiseSVN，而应该专注于它没有重点优化的工作流：

- 用现代化界面审查本地改动。
- 在同一个文件里只选择部分 hunk 或行提交。
- 把一大批本地改动拆成多个干净的提交。
- 在提交前发现高风险改动。
- 对 Unity/游戏项目提供更贴近实际工作的检查。
- 保存提交草稿和审查状态。

如果 NovaSVN 作为开源项目推进，最合理的方向是“小而强”：先解决真实 SVN 团队每天会遇到的提交痛点，而不是追求完整覆盖所有 SVN 功能。

## 推荐范围

NovaSVN 第一阶段应该是一个提交/审查工作台，而不是完整 SVN 客户端。

核心流程：

```text
打开工作副本 -> 审查本地改动 -> 选择要提交的内容 -> 运行安全检查 -> 提交
```

第一阶段重点功能：

1. 本地改动仪表盘
2. 现代化 diff 查看器
3. 文件级提交
4. 文本文件的 hunk/行级部分提交
5. 提交信息编辑器和模板
6. 提交前安全检查
7. 提交草稿

暂缓功能：

- 完整仓库浏览器
- 分支/标签管理 UI
- 合并 UI
- Blame 视图
- 完整冲突解决器
- Explorer 右键菜单集成
- 完整替代 TortoiseSVN

## 差异化功能

### 部分提交

SVN 没有 Git 那样的 index，所以普通 SVN 客户端通常只能按文件提交。NovaSVN 可以在工具层提供类似 Git partial commit 的体验，让用户在 diff 里选择 hunk 或行。

第一版限制：

- 只支持文本文件
- 优先支持已修改文件
- 不处理二进制文件
- 不处理复杂移动/重命名
- 第一版不处理仅属性变更

### 提交审查模式

NovaSVN 应该像一个轻量级 pre-commit review 工具：

- 标记文件已审查/未审查。
- 按类型或模块显示改动统计。
- 搜索 changed lines 里的风险内容，例如 debug 代码、TODO、临时路径、日志输出。
- 对大文件、二进制改动、异常生成文件给出提醒。
- 保存审查状态，后续通过提交草稿恢复。

### 智能改动分组

NovaSVN 可以帮助用户把本地改动拆成更清晰的提交：

- 按目录或模块分组。
- 把 Unity `.meta` 文件和对应资源配对。
- 分开显示源码、资源、配置、项目设置等类型。
- 支持手动勾选、拖拽或移动到提交草稿。

### 提交草稿

提交草稿保存一次准备提交的上下文：

- 已选择文件
- 已选择 hunk 或行
- 提交信息
- 审查状态
- 已忽略或确认的警告

这可以让用户从一大批本地改动里准备多个提交，而不是只能一次性处理。

### 提交前安全检查

提交前 NovaSVN 应该检查：

- 工作副本是否有冲突。
- 是否存在 missing、obstructed 等异常文件。
- 新增文件是否还没有加入版本控制。
- 是否误包含日志、临时文件、生成文件。
- 是否存在 mixed revision 状态。
- Unity `.meta` 和资源文件是否配对。
- 是否有意外的大型二进制或资源文件变更。

## Unity 和游戏项目支持

如果初始用户主要来自 Unity 或游戏开发团队，NovaSVN 可以快速形成差异化：

- `.meta` 配对提醒
- Scene/Prefab YAML diff 可读性优化
- 大资源文件变更提醒
- Addressables、ProjectSettings、Packages 变更分组
- 二进制资源锁定状态提示
- Unity 常见临时文件和生成文件过滤

这些能力应该是可选的，并根据项目结构自动识别。

## 技术架构

推荐技术栈：

```text
前端：Tauri + Svelte + TypeScript
Diff UI：Monaco Editor
后端：Rust
SVN 集成：第一版调用 svn 命令行
打包：Tauri bundler
```

这个方案原则上跨平台：

- Windows
- macOS
- Linux

但 MVP 建议优先聚焦 Windows，因为 Windows + TortoiseSVN 是非常常见的 SVN 使用场景，也更贴近当前目标用户。

## 为什么选择 Tauri

Tauri 提供轻量级桌面外壳，后端使用 Rust，前端使用 Web 技术。它可以让 NovaSVN 拥有现代化 UI，同时避免 Electron 带来的较大体积。

优势：

- 适合桌面开发者工具
- 包体通常比 Electron 小
- 可以使用原生文件选择器和系统集成能力
- Rust 后端适合管理进程、路径、patch 和 shadow working copy
- Web 前端更容易快速做出美观、专业的 UI

## SVN 集成：优先使用 svn 命令行

第一版建议调用 SVN 命令行客户端，而不是直接链接 libsvn。

可使用命令：

```text
svn status --xml
svn diff
svn info --xml
svn commit
svn update
svn revert
svn patch
svn cleanup
```

优点：

- 实现速度快
- 容易调试
- 行为与用户命令行一致
- 避免 libsvn、APR、DLL 集成复杂度
- 对开源贡献者更友好

后端应该抽象出 `SvnClient` 接口，未来如果命令行方式不够用，可以再替换或增加 libsvn 实现。

## svn.exe 和 libsvn 的区别

`svn.exe` 是命令行程序。NovaSVN 可以启动子进程运行它，并优先解析 XML 等结构化输出。

`libsvn` 是 Subversion 底层库 API。它提供更深的控制能力，例如结构化错误、认证回调、进度回调和更细粒度的工作副本操作，但也会显著增加集成复杂度，尤其是在 Windows 上。

推荐路线：

```text
MVP：使用 svn.exe
未来：只有在命令行集成明显受限时，再考虑 libsvn 后端
```

## 影子工作副本

影子工作副本是 NovaSVN 管理的一份临时 SVN working copy。它用于安全执行那些如果直接在用户真实工作区操作会比较危险的流程，尤其是部分提交。

例子：

```text
真实工作副本：
  A.cs = 改动 1 + 改动 2 + 改动 3

用户想提交：
  只提交改动 1 + 改动 3

影子工作副本：
  A.cs = 只应用改动 1 + 改动 3
  svn commit 在这里执行
```

为什么需要它：

- 不临时修改用户真实文件。
- 部分提交失败时不会破坏真实工作区。
- NovaSVN 可以在可控目录中拼出“本次提交应该包含的内容”。
- 用户真实工作副本仍然可以继续查看或编辑。

它可以类比 Git worktree 的用途，但底层并不一样。Git worktree 是 Git 原生功能，并共享对象库；SVN 没有原生 worktree 概念，影子工作副本是 NovaSVN 自己维护的另一份 SVN working copy，拥有自己的 `.svn` 元数据。

## 部分提交实现策略

### 策略 A：临时修改真实工作副本

流程：

1. 保存完整 patch。
2. 从真实工作副本中临时撤掉未选择的 hunk。
3. 执行 `svn commit`。
4. 恢复未选择的 hunk。

优点：

- 实现较简单
- 不需要额外 checkout 或缓存

缺点：

- 风险较高
- 会临时改变用户真实文件
- 程序崩溃或 patch 恢复失败时比较麻烦
- 用户心理负担更重

### 策略 B：影子工作副本

流程：

1. 从真实工作副本读取当前 diff。
2. 生成只包含选中 hunk 的 patch。
3. 准备或更新影子工作副本到正确 base revision。
4. 在影子工作副本应用选中 patch。
5. 从影子工作副本提交。
6. 提交成功后，引导用户更新真实工作副本或由工具辅助同步状态。

优点：

- 更安全
- 失败时更容易恢复
- 更适合作为长期 partial commit 基础

缺点：

- 实现复杂
- 占用更多磁盘空间
- 需要仔细处理 revision、路径、文件状态和冲突

推荐：

```text
正式 partial commit 使用影子工作副本。
临时修改真实工作副本只适合实验功能，且必须明确标为不安全。
```

## MVP 路线图

### 版本 0.1：基础提交工作台

- 选择/打开 SVN 工作副本
- 检测 `svn` 命令行路径
- 显示 `svn info`
- 显示 `svn status --xml`
- 展示本地改动文件列表
- 显示文件 diff
- 勾选文件
- 输入提交信息
- 提交选中文件
- 显示命令输出和错误

### 版本 0.2：现代化 Diff 审查

- Monaco diff 查看器
- 语法高亮
- inline / side-by-side 模式
- whitespace 显示开关
- 文件已审/未审状态
- 基础安全检查
- 提交信息模板

### 版本 0.3：实验性部分提交

- 解析 unified diff 为文件和 hunk
- 支持选择 hunk
- 生成 selected patch
- 在影子工作副本应用 selected patch
- 从影子工作副本提交
- 限制为文本文件修改

### 版本 0.4：草稿和智能分组

- 保存提交草稿
- 恢复已选择文件/hunk
- 自动分组文件
- Unity `.meta` 配对检查
- 警告确认/忽略状态

## UI 方向

NovaSVN 应该看起来像一个专业开发者工具：

- 信息密度适中
- 配色克制
- 层级清晰
- 键盘操作顺畅
- 应用首屏就是工作台，不做营销式 landing page
- 避免过大的装饰性 UI
- 像一个认真可靠的提交仪表盘，而不是玩具项目

建议布局：

```text
左侧栏：
  工作副本、视图、过滤器

中间区域：
  按状态/模块分组的改动文件列表

右侧或主区域：
  Diff 查看器和审查控件

底部区域：
  提交信息、警告、已选改动摘要、提交按钮
```

重要 UI 原则：

- 常用操作使用图标按钮。
- 控件保持紧凑。
- 文件行、状态标签、工具栏按钮应有稳定尺寸。
- 避免卡片套卡片。
- 主要工作区域应是完整工作面板，而不是装饰性模块。
- 警告必须可操作，不能只是制造噪音。

## 开源策略

如果目标是开源项目，建议从一开始就公开仓库和设计边界。

仓库应重点准备：

- 清晰 README
- 明确 scope 和 non-goals
- 早期截图或 GIF
- 现实的路线图
- Issue 模板
- 架构文档
- partial commit 安全说明

推荐 README 定位：

```text
NovaSVN is not a replacement for TortoiseSVN.
It is a focused commit workspace for Subversion users who want better change review,
safer commit preparation, and Git-like partial commit workflows.
```

中文定位可以写成：

```text
NovaSVN 不是 TortoiseSVN 的替代品，而是面向 SVN 用户的现代化提交工作台，
专注于本地改动审查、安全提交准备，以及类似 Git 的部分提交体验。
```

## 风险

技术风险：

- 部分提交正确性
- patch 应用失败
- mixed revision 工作副本
- 文件移动/重命名
- SVN properties
- 二进制文件
- 认证和凭据弹窗
- 跨平台 SVN 命令差异

产品风险：

- 在验证提交流程前做太多功能
- 直接与 TortoiseSVN 做完整竞争
- 过度适配单一团队工作流
- partial commit 给用户不安全感

缓解方式：

- 第一版范围要小。
- 实验功能明确标识。
- 使用影子工作副本保护真实文件。
- 在一次性 SVN 测试仓库里验证流程后，再用于真实项目。
- 增加 dry-run 和 preview 模式。

## 成功标准

NovaSVN 值得继续投入的信号：

- 开发者自己更愿意用它替代 TortoiseSVN 的 commit 窗口。
- 常见文本文件的部分提交稳定可用。
- 审查模式能真实发现提交前错误。
- 应用在提交准备场景下比 TortoiseSVN 更快、更清晰。
- 项目价值可以用一句话说清楚。

一句话价值：

```text
NovaSVN 是一个现代化 Subversion 提交工作台，专注于精准改动审查和更安全的提交流程。
```
