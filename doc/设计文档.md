# NovaSVN 设计文档

## 项目定位

NovaSVN 是一个现代化、高性能、跨平台的完整 Subversion 客户端。它面向仍在使用 SVN 的个人、团队和游戏项目，目标是在保留 SVN 成熟工作流的基础上，提供接近现代 Git 客户端的交互体验。

NovaSVN 不只是一个提交窗口，也不只是 TortoiseSVN 的外壳补充。它应该覆盖常用 SVN 客户端能力，并在本地改动审查、虚拟暂存区、部分提交、分支工作区、多任务开发和大型工作副本性能上形成自己的特色。

一句话定位：

```text
NovaSVN 是一个现代化 SVN 客户端，提供完整 SVN 能力、Git-like 暂存体验、部分提交和高性能跨平台工作台。
```

可选英文标语：

- A modern Subversion client for focused development.
- Subversion workflow, modernized.
- Fast SVN client with Git-like staging.

中文定位：

- 现代化 SVN 桌面客户端
- 高性能 Subversion 工作台
- 具备 Git-like 暂存和部分提交能力的 SVN 客户端

## 核心价值

NovaSVN 的价值不是简单复制已有 SVN 客户端，而是解决 SVN 团队在现代开发流程中的痛点：

- **完整能力**：覆盖 checkout、update、commit、diff、log、branch、tag、switch、merge、lock、resolve、repository browser 等常用 SVN 操作。
- **现代界面**：提供清晰、紧凑、响应快的工作台 UI，而不是依赖分散的系统菜单和多个弹窗。
- **极快响应**：面向大型工作副本优化状态扫描、改动列表、diff、搜索、分组和后台任务。
- **Git-like 暂存区**：在 SVN 没有 index 的前提下，提供已暂存/未暂存的提交准备体验。
- **部分提交**：支持文件级提交，并逐步支持文本文件 hunk 级、行级部分提交。
- **分支工作区**：用多工作副本池解决 SVN 分支切换慢、易受本地改动影响的问题。
- **跨平台体验**：使用统一的 Tauri 应用覆盖 Windows 和 macOS，常用操作可通过系统右键菜单进入。
- **游戏项目友好**：对 Unity、资源文件、`.meta` 配对、大文件和生成文件提供更贴近实际工作的检查。

## 目标用户

NovaSVN 优先面向以下用户：

- 使用 SVN 的 Windows 和 macOS 开发者。
- 需要完整 SVN GUI，但希望 UI 更现代、响应更快的团队。
- 经常在一个工作副本中堆积大量本地改动，需要拆分成多个提交的开发者。
- 希望在 SVN 中获得类似 Git staged/unstaged 工作流的用户。
- Unity、游戏、工具链项目中需要管理资源、Prefab、Scene、`.meta` 和大型二进制文件的团队。
- 希望用多个本地分支工作区并行处理需求、修复和实验任务的团队。

## 与 TortoiseSVN、SmartSVN 的区别

TortoiseSVN、SmartSVN 都是成熟工具，NovaSVN 不应该通过“功能更多”来证明价值，而应该通过更现代、更快、更适合提交组织和多任务开发的体验形成差异。

### 与 TortoiseSVN 的区别

TortoiseSVN 的优势：

- 与 Windows Explorer 深度集成。
- 右键菜单和图标覆盖成熟。
- 基础 SVN 操作稳定。
- Windows 用户认知度高。

NovaSVN 的侧重点：

- 提供独立的现代化工作台，而不是主要依赖 Explorer 上下文菜单。
- 提供虚拟暂存区、部分提交、提交草稿和审查状态。
- 支持 Windows 和 macOS 的一致应用体验。
- 优化大型工作副本的状态展示、过滤、搜索和 diff。
- 不做状态图标覆盖，降低 Shell 集成复杂度和稳定性风险。
- Windows 右键菜单只作为常用功能入口，复杂流程回到 NovaSVN 内完成。

### 与 SmartSVN 的区别

SmartSVN 的优势：

- 跨平台完整 SVN GUI。
- 功能覆盖广，适合传统 SVN 管理场景。
- 具备日志、分支、合并、仓库浏览等完整客户端能力。

NovaSVN 的侧重点：

- 更强调高性能本地工作台和现代 UI 体验。
- 把 Git-like 暂存区作为核心交互模型。
- 重点支持文件/hunk 级部分提交。
- 用多工作副本池提供更快的本地分支切换体验。
- 加强提交前安全检查、智能分组、Unity/游戏项目规则。
- 面向高频提交和多任务并行开发做专门优化。

## Git-like 虚拟暂存区

SVN 没有 Git index，不能天然支持 staged/unstaged 模型。NovaSVN 应该在工具层提供一个虚拟暂存区，让用户用类似 Git 的方式准备提交。

### 暂存区目标

暂存区需要支持：

- 把本地改动分为未暂存和已暂存。
- 文件级暂存 modified、added、deleted。
- 文本文件 hunk 级暂存。
- 后续支持行级暂存。
- 保存提交草稿。
- 恢复审查状态。
- 提交前预览真正要提交的内容。
- 文件内容变化后检测草稿是否失效。

### 暂存区不是 SVN 元数据

虚拟暂存区不修改 SVN 的 `.svn` 元数据，也不把 SVN 改造成 Git。它保存的是 NovaSVN 自己维护的选择状态：

- 工作副本标识
- 文件路径
- 文件状态
- 文件内容摘要
- 已选择文件
- 已选择 hunk
- 提交信息
- 审查状态
- 已确认或忽略的警告

### UI 模型

本地改动视图默认分为：

```text
未暂存
已暂存
未版本控制
异常状态
```

用户可以：

- 点击文件旁按钮暂存/取消暂存。
- 在 diff 中选择 hunk。
- 查看已暂存内容预览。
- 从已暂存内容提交。
- 将本次选择保存为提交草稿。

## 部分提交

部分提交是 NovaSVN 的核心特色之一。目标是在 SVN 工作流中提供接近 Git partial commit 的体验。

### 第一阶段限制

第一阶段只支持：

- 已版本控制文本文件。
- modified 状态。
- hunk 级选择。
- 使用影子工作副本执行提交。

第一阶段不支持：

- 二进制文件部分提交。
- 属性-only 变更部分提交。
- 复杂 move/rename 部分提交。
- 冲突文件部分提交。
- mixed revision 工作副本中的部分提交。
- 行级部分提交。

### 影子工作副本

影子工作副本是 NovaSVN 管理的一份临时 SVN working copy，用于安全执行部分提交。

例子：

```text
真实工作副本：
  A.cs = 改动 1 + 改动 2 + 改动 3

用户想提交：
  只提交改动 1 + 改动 3

影子工作副本：
  A.cs = 只应用改动 1 + 改动 3
  svn commit 在影子工作副本中执行
```

这样可以避免临时改写用户真实文件。即使 patch 应用失败或提交失败，也不会破坏真实工作副本。

### 部分提交流程

```text
1. 从真实工作副本读取 svn diff。
2. 解析 unified diff，得到文件和 hunk。
3. 用户选择要提交的 hunk。
4. NovaSVN 生成 selected patch。
5. 准备或更新影子工作副本到对应 base revision。
6. 在影子工作副本应用 selected patch。
7. 执行 svn diff 生成提交预览。
8. 用户确认后从影子工作副本提交。
9. 提交成功后刷新真实工作副本状态。
10. 提示用户 update，或由 NovaSVN 辅助同步。
```

### 失败处理

以下情况必须阻止部分提交：

- 工作副本存在冲突。
- 文件存在 tree conflict。
- 文件是 binary。
- 文件只有属性变更。
- 工作副本 mixed revision 未通过校验。
- 影子工作副本无法更新到正确 revision。
- selected patch 无法干净应用。
- 提交前远端已产生冲突性变化。

失败时 NovaSVN 应该：

- 不修改真实工作副本。
- 保留暂存草稿。
- 显示失败原因。
- 提供重新扫描、重建影子副本、清空暂存区等操作。

## SVN 分支与 Git 分支

NovaSVN 需要清楚解释 SVN 分支和 Git 分支的差异，因为很多用户会把“快速切换分支”的 Git 体验直接套到 SVN 上。

### Git 分支

Git 分支本质上是本地仓库中的轻量引用。常见情况下，切换分支主要是移动 HEAD，并把工作区更新到目标提交。

Git 分支特点：

- 分支主要存在于本地仓库。
- 创建和切换很快。
- 可以离线创建、提交和切换。
- 多分支开发是 Git 的核心模型。
- index 支持暂存区和部分提交。

### SVN 分支

SVN 分支通常是仓库中的目录拷贝。常见仓库结构：

```text
/trunk
/branches/feature-a
/branches/bugfix-b
/tags/v1.0.0
```

SVN 分支特点：

- 分支是远端仓库中的路径。
- 创建分支通常是 repository copy。
- 工作副本通常绑定到某个 URL。
- 切换分支一般使用 `svn switch`。
- 没有 Git index。
- 本地提交必须直接提交到远端仓库。

### svn switch 的问题

`svn switch` 可以让同一个工作副本从一个分支 URL 切到另一个分支 URL。它节省磁盘，但有明显限制：

- 切换速度受仓库大小和网络影响。
- 本地未提交改动可能阻塞切换。
- 容易出现冲突或 tree conflict。
- 切换前后工作副本状态需要重新扫描。
- 不适合频繁在多个任务之间来回切换。

## 多工作副本分支池

为了提供接近 Git 的快速分支切换体验，NovaSVN 默认使用多工作副本分支池，而不是把 `svn switch` 作为主流程。

### 核心思想

每个活跃 SVN 分支对应一个本地工作副本：

```text
NovaSVN Workspace Pool
  trunk/              -> svn://repo/project/trunk
  feature-login/      -> svn://repo/project/branches/feature-login
  hotfix-crash/       -> svn://repo/project/branches/hotfix-crash
```

应用内切换分支时，NovaSVN 只是切换当前工作区视图，不需要立即执行 `svn switch`。这可以让多任务开发接近即时切换。

### 分支池能力

- 从 trunk 创建新分支。
- 从远端 branches 打开分支。
- 为分支创建或复用本地工作副本。
- 显示每个分支的本地路径、仓库 URL、当前 revision、本地改动数量。
- 支持标记常用分支。
- 支持清理不再使用的分支工作副本。
- 每个分支拥有独立暂存草稿。
- 每个分支拥有独立提交计划和审查状态。

### 任务工作区

建议在分支池之上增加任务工作区概念：

```text
任务 = SVN 分支 + 本地工作副本 + 暂存草稿 + 提交计划 + 审查状态
```

这样用户可以同时维护：

- 一个主线同步任务。
- 一个功能开发任务。
- 一个线上修复任务。
- 一个实验验证任务。

NovaSVN 应该让用户在这些任务之间快速切换，而不是频繁执行 `svn switch`。

### svn switch 的定位

NovaSVN 仍然保留 `svn switch`，但作为高级操作：

- 用户明确要复用当前工作副本时使用。
- 执行前必须检查本地改动。
- 有本地改动时必须提醒风险。
- 执行后必须重新扫描状态。
- 出现冲突时进入冲突处理视图。

## Windows 和 macOS 右键菜单

NovaSVN 需要提供系统右键菜单入口，但不做状态图标覆盖。

### Windows Explorer 入口

在 Windows 上提供常用右键菜单：

- Open in NovaSVN
- Commit
- Update
- Diff
- Log
- Revert
- Cleanup
- Branch Workspace

右键菜单用于快速启动常用流程。复杂操作进入 NovaSVN 应用内完成。

### macOS Finder 入口

在 macOS 上提供同等常用入口：

- Open in NovaSVN
- Commit
- Update
- Diff
- Log
- Revert
- Cleanup
- Branch Workspace

macOS 的实现方式可以采用 Finder 服务、Quick Action 或系统扩展能力，具体以 Tauri 打包和系统权限限制为准。

### 不做状态图标覆盖

NovaSVN 第一阶段不做文件状态图标覆盖：

- 避免 Windows Shell overlay 数量限制。
- 降低系统扩展稳定性风险。
- 避免 macOS Finder 扩展复杂度。
- 把状态展示集中在 NovaSVN 应用内完成。

## 技术架构

NovaSVN 使用原设计推荐技术栈：

```text
前端：Tauri + Svelte + TypeScript
Diff UI：Monaco Editor
后端：Rust
SVN 集成：第一版调用 svn 命令行
打包：Tauri bundler
```

### 为什么选择 Tauri

Tauri 提供轻量级桌面外壳，后端使用 Rust，前端使用 Web 技术。它适合构建现代开发者工具：

- 包体通常比 Electron 小。
- 可以使用原生文件选择器和系统能力。
- Rust 后端适合管理进程、路径、缓存、patch 和影子工作副本。
- Svelte + TypeScript 适合构建高响应工作台 UI。
- Monaco Editor 适合提供专业 diff 和代码查看体验。

### 前端职责

前端负责：

- 工作台布局。
- 改动列表。
- 暂存区交互。
- Diff 查看器。
- 日志和仓库浏览。
- 分支池界面。
- 提交信息编辑器。
- 安全检查结果展示。
- 命令面板和快捷键。
- 任务队列状态。

### Rust 后端职责

后端负责：

- 调用 `svn` 命令行。
- 解析 `svn status --xml`、`svn info --xml`、`svn log --xml`。
- 管理工作副本状态缓存。
- 管理虚拟暂存区。
- 解析 diff 和生成 selected patch。
- 管理影子工作副本。
- 管理分支工作副本池。
- 管理后台任务队列。
- 处理认证、错误、取消和日志。

### SVN 集成

第一版优先使用 `svn` 命令行，而不是直接链接 libsvn。

可使用命令：

```text
svn checkout
svn update
svn status --xml
svn info --xml
svn diff
svn log --xml
svn commit
svn add
svn delete
svn move
svn copy
svn revert
svn cleanup
svn lock
svn unlock
svn resolve
svn merge
svn switch
svn list --xml
svn propget
svn propset
svn patch
```

优点：

- 实现速度快。
- 行为与用户命令行一致。
- 容易调试。
- 避免 libsvn、APR、DLL 集成复杂度。
- 对开源贡献者更友好。

后端应该抽象出 `SvnClient` 接口。未来如果命令行方式不够用，再增加 libsvn 后端。

## 高性能设计

NovaSVN 必须优先服务大型工作副本，目标场景是数万文件、数千改动、较多资源文件和长耗时 SVN 命令。

### 状态扫描

- 启动后先显示上次缓存状态。
- 后台执行 `svn status --xml` 刷新真实状态。
- 文件变化通过 watcher 触发局部刷新。
- SVN 命令结果是最终真相。
- 扫描任务可取消。
- 多个刷新请求需要合并，避免重复扫描。

### 改动列表

- 使用虚拟滚动。
- 支持按目录、状态、文件类型、模块分组。
- 支持快速过滤。
- 支持 changed lines 搜索。
- 支持只看已暂存、未暂存、异常、未审查。
- 支持目录级统计缓存。

### Diff 性能

- Diff 懒加载。
- 大文件降级展示。
- 二进制文件不尝试文本 diff。
- Monaco Editor 只加载当前可见文件。
- 支持取消正在生成的 diff。
- 支持缓存最近查看过的 diff。

### 后台任务

长耗时任务必须进入任务队列：

- checkout
- update
- commit
- merge
- switch
- cleanup
- branch workspace checkout
- repository browser 大目录加载

任务队列需要支持：

- 进度展示。
- stdout/stderr 日志。
- 取消。
- 重试。
- 失败原因。
- 不阻塞 UI。

## UI 信息架构

NovaSVN 的首屏应该是工作台，而不是营销式首页。

### 主布局

```text
左侧栏：
  工作区
  分支池
  仓库
  草稿
  过滤器

中间区域：
  本地改动
  暂存区
  日志
  分支
  仓库浏览

右侧区域：
  Diff
  文件详情

  检查结果

底部区域：
```

### 设计原则

- 信息密度适中。
- 控件保持紧凑。
- 文件行、状态标签、工具栏按钮尺寸稳定。
- 常用操作使用图标按钮。
- 复杂操作进入命令面板或上下文菜单。
- 警告必须可操作。
- 不做卡片套卡片。
- 不使用过度装饰性的 UI。
- 键盘操作必须顺畅。
- 大型列表必须保持滚动流畅。

### 核心视图

- 本地改动视图。
- 暂存区视图。
- 提交视图。
- 日志视图。

- 显示文件 diff。
- 文件级 staged/unstaged。
- 输入提交信息。
- 提交已暂存文件。
- Update、Revert、Cleanup。
- 显示命令输出和错误。

## 风险与缓解

### 技术风险

- 部分提交正确性。
- 影子工作副本 revision 对齐。
- mixed revision 工作副本。
- patch 应用失败。
- 文件移动/重命名。
- SVN properties。
- 二进制文件。
- 认证和凭据弹窗。
- 跨平台 `svn` 命令差异。
- Windows/macOS 右键菜单实现差异。
- 大型工作副本性能。

### 产品风险

- 完整客户端范围过大。
- 过早与成熟客户端做全量竞争。
- 暂存区模型让用户误以为 SVN 原生支持 Git index。
- 多工作副本分支池占用磁盘。
- 高级 SVN 功能边界复杂。

### 缓解方式

- 分阶段实现完整客户端。
- 第一版先打通工作副本和提交闭环。
- 暂存区明确标注为 NovaSVN 虚拟暂存。
- 部分提交必须使用影子工作副本。
- 复杂状态先阻止，再逐步支持。
- 大型工作副本从第一版就设计缓存、虚拟列表和后台任务。
- 右键菜单只做常用入口，不做状态图标覆盖。
- 所有长任务都提供日志、取消和失败恢复建议。

## 验收标准

NovaSVN 值得继续投入的信号：

- 可以替代 TortoiseSVN 或 SmartSVN 的高频日常操作。
- 大型工作副本打开、过滤、滚动、diff 响应明显更流畅。
- 文件级暂存和提交稳定可用。
- hunk 级部分提交不会破坏真实工作副本。
- 多工作副本分支池能显著降低多任务切换成本。
- Windows 和 macOS 都能通过右键菜单进入常用操作。
- Unity/游戏项目检查能真实发现提交前错误。
- 项目价值可以用一句话说清楚。

一句话价值：

```text
NovaSVN 是一个现代化、高性能的完整 SVN 客户端，用 Git-like 暂存区、部分提交和多工作副本分支池改善传统 SVN 开发体验。
```
