# xflow Do

## 目标

执行已有 xflow 任务 Spec 中的任务列表。

不要预先生成 `.xflow/`。只有当实现本身需要某个目录或文件，并且它还不存在时，才创建它。

## 命令

以下写法等价：

- `/xflow-do <feature-name-or-file>`
- `/xflow:do <feature-name-or-file>`
- `xflow do <feature-name-or-file>`

## 输入解析

1. 如果 `<feature-name-or-file>` 指向一个已存在文件，直接读取该文件作为任务 Spec。
2. 否则，保留用户输入的原始名称，读取 `.xflow/tasks/<feature-name-or-file>.md`。
3. 如果找不到 Spec 文件，停止并告诉用户检查过哪些路径。
4. 如果存在多个类似任务的章节，优先使用 `## 任务列表`、`## Task List`、`## Tasks` 或 `## Todo`。

## 流程

1. 如果 `.xflow/ai-context.md` 存在，先读取它再开始实现。
2. 读取解析到的任务 Spec。
3. 从 markdown checkbox 中提取任务列表：
   - 未完成任务：`- [ ]`、`* [ ]` 或 `+ [ ]`。
   - 已完成任务：`- [x]`、`* [x]` 或 `+ [x]`。
4. 如果 Spec 中没有未完成任务列表，停止并询问用户是要先补充任务，还是按某条明确指令继续。
5. 按 Spec 顺序执行未完成任务。
6. 修改范围必须限制在 Spec 内。除非用户明确扩大范围，否则不要实现 Spec 之外的要求。
7. 每个任务只有在对应实现和验证完成后，才在 Spec 中标记为完成。
8. 如果某个任务被缺失信息、失败测试或冲突要求阻塞，停止，保持该任务未勾选，并提出聚焦问题。
9. 所有任务完成后，总结实现内容和验证结果。

## 任务更新

- 保留用户原始任务描述。
- 完成任务时只把 checkbox 从未完成改为已完成。
- 除非用户要求，不要删除任务、重排任务或重写 Spec。

## 验证

- 针对已实现改动运行最小且有用的验证命令。
- 如果无法运行验证，说明原因。
- 如果代码和 Git 状态与 Spec 不一致，以代码和 Git 状态为事实来源。

## 原则

- Spec = 实现计划。
- 代码 + Git = 真相。
- 只完成任务列表要求的内容。
